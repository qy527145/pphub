## 〇、贯穿全局的 5 条硬约束（决定整体架构，务必先读）

1. **WebRTC 默认就是加密的，但「E2EE」是有条件的。** 媒体走 DTLS-SRTP、数据通道走 DTLS/SCTP，浏览器里**没有明文模式**。但握手用的证书指纹是通过信令服务器交换的——**恶意/被入侵的信令服务器可以做中间人攻击**。要对得起 PRD 里「端到端加密」的宣称，必须提供**带外指纹校验（SAS，如 emoji/数字串对比）**。纯 1:1 P2P 才是真 E2EE；一旦引入 SFU 转发，服务器就能看到明文（除非再叠加 Insertable Streams + SFrame）。

2. **NAT 穿透必须要有 TURN 兜底，不能只靠 STUN。** 现实中约 **10–20%** 的连接（对称 NAT、运营商级 NAT/CGNAT、移动网络、企业防火墙）**穿不透，必须经 TURN 中转**。PRD 写「预留 TURN 配置项」是不够的——要真正规划部署（自建 coturn / eturnal，或用 Cloudflare Realtime TURN 按量付费）。TURN 中转是要花服务器带宽和钱的，这与「零服务器带宽」的定位有冲突，需要接受这个现实。

3. **HTTP 局域网 IP 不是安全上下文。** `http://192.168.x.x` / `http://10.x.x.x` 在所有浏览器里都是**不安全源**：`getUserMedia`（摄像头/麦克风/屏幕）、`crypto.subtle`、Service Worker、剪贴板 API **全部不可用**。只有 `https://`、`http://localhost`、`http://127.0.0.1` 是安全上下文。**唯一例外**：`RTCPeerConnection` 本身不要求安全上下文——所以「纯数据通道」的局域网直连（文件/聊天）能在 `http://LAN-IP` 上跑，但**局域网摄像头监控这类要 getUserMedia 的功能，在 http 局域网 IP 上跑不了**，必须解决 HTTPS 证书问题。

4. **浏览器有一道铁墙：不能注入输入、不能开 shell/PTY、不能开原始 socket、不能后台常驻。** 这直接判了 PRD 里「远程桌面控制」「网页版 SSH 终端」的死刑——**纯浏览器永远做不到**。要做只能配一个**可选的原生伴侣程序（Rust 二进制）**装在被控端。这是最大的一个架构岔路口。

5. **纯 Mesh 音视频最多 4–6 人。** 每多一个人，每个端就要多编码+上传一路流；硬件编码器通常只支持 3–4 路并发。**视频房间超过 5–6 人就必须上 SFU**（但 SFU 会占服务器带宽、且破坏 E2EE 与「零带宽」定位）。纯音频 Mesh 可以更多。数据通道 Mesh 可到 50–100 端。

## 模块 1：文件与数据传输（核心基础）

### 1.1 大文件与文件夹无缝快传 — ✅ 可行（有浏览器差异，需分平台降级）
- **能做**：`RTCDataChannel` 分块传输，配合 `bufferedAmount` 背压。局域网/本机实测可达 **300Mbps–1Gbps+**（Chrome dcSCTP 之后）；公网受 SCTP 接收窗口/RTT 限制，通常几十 Mbps。
- **关键约束**：
  - 单条消息不能超过协商的 `maxMessageSize`（libwebrtc 系 256KiB），**超了会直接抛错/断通道，没有跨浏览器自动分片**。分块建议 16–64KiB。
  - 落盘：**File System Access API（边收边写磁盘）只有 Chromium 有**；Safari/Firefox 没有文件选择器，只能先写 **OPFS** 暂存再 `<a download>` 导出。内存里攒 Blob 桌面别超 ~1GB、移动端几百 MB（iOS 到 ~1–1.5GB 会被系统杀进程）。
  - 文件夹上传：`webkitdirectory` 桌面全支持，**iOS Safari 要 18.4+**。
- **建议**：列为 **Phase 1 核心**，按 Chromium（流式落盘）/ Safari·Firefox（OPFS 暂存）两条落盘路径实现。

### 1.2 跨设备云剪贴板 — ⚠️ 受限，必须降级（不能后台监听）
- **做不到**：PRD 描述的「两端开启剪贴板监听，一端复制对端自动接收」——**浏览器绝不允许后台/失焦时读剪贴板**。`clipboardchange` 事件只有 Chrome 144+ 有且要求页面聚焦。
- **能做（降级 UX）**：① 手动「发送剪贴板」按钮；② 页面重新获得焦点时（`focus`/`visibilitychange`）读一次；③ 标准 `paste` 事件（Ctrl/Cmd+V 或「粘贴」按钮）。格式支持 text / HTML / PNG。
- **建议**：保留功能但**明确改名为「一键剪贴板互传 / 聚焦同步」**，去掉「自动监听」的承诺。真要后台自动同步，只能靠原生伴侣程序或浏览器扩展。

### 1.3 无网/局域网离线快传 — ⚠️ 受限可行（数据通道 OK，媒体不行）
- **能做**：数据通道不要求安全上下文，所以两台设备同一 Wi-Fi 下，通过**手动输入对方 IP + 局域网内的信令**（本机 WS 服务 / 手动复制 SDP / 二维码）可以直连传文件、聊天。离线时不配 STUN/TURN，只收集 host candidate，反而握手更快。
- **关键约束**：
  - **纯浏览器无法发现局域网内的对端**（没有 UDP/mDNS/socket API，老的 IP 探测手段已被 Chrome 142+ 的「本地网络访问」权限封掉）。只能：用户手输 IP / 扫码 / 复制粘贴 SDP。
  - mDNS 混淆候选（`.local`）会让局域网直连**依赖组播可达**——很多访客/企业 Wi-Fi 开了 AP 隔离会静默失败。
  - 局域网 http IP 下 **getUserMedia 用不了**（见硬约束 3）。
- **建议**：Phase 4 做。基础版=手输 IP + 二维码信令；如需「自动发现」，归入原生伴侣程序能力（mDNS 广播/发现）。

## 模块 2：远程共享与控制（极客运维）

### 2.1 高清屏幕共享 + 互动白板 — ✅ 可行（屏幕共享桌面限定）
- **能做**：`getDisplayMedia` 桌面全支持；白板坐标走 DataChannel、接收端 Canvas 叠加在 video 上。白板共享状态建议用 **CRDT（Yjs）** 做多端一致。
- **关键约束**：
  - **iOS/Android 浏览器完全不支持屏幕共享**（`getDisplayMedia` 在移动端不存在）。
  - 系统/标签页音频抓取：只有 Chromium 能抓标签页音频，系统音频仅 Windows/ChromeOS；Firefox/Safari 抓不到共享音频。
  - 屏幕共享要安全上下文（HTTPS）。
- **建议**：列为 **Phase 2/3**。白板是强互动亮点，建议做。

### 2.2 轻量级远程桌面控制 — 🔶 需原生伴侣程序（纯浏览器 ❌）
- **做不到**：浏览器**不能向操作系统注入键鼠事件**（`isTrusted=false` 的合成事件不算数），这是安全铁墙。Chrome 的 Captured Surface Control 只能对「被捕获的标签页」做滚动/缩放，**不能真正控制桌面**。
- **能做（需伴侣）**：被控端装 Rust 伴侣程序，用 `enigo` 注入键鼠。**macOS 需要用户在系统设置授予「辅助功能」权限，且程序必须签名**；Windows 无运行时弹窗但受 UIPI 限制（普通权限进程无法控制管理员窗口）；Linux Wayland 支持很零碎。
- **建议**：**先由你决定是否引入原生伴侣程序**。若引入，可做；若坚持纯浏览器/免安装，此功能删除。

### 2.3 网页版免密 SSH 终端 — 🔶 需原生伴侣程序（纯浏览器 ❌）
- **做不到**：浏览器**不能开 PTY/shell、不能开原始 TCP socket**。
- **能做（需伴侣）**：xterm.js 做前端终端界面，真正的 PTY/SSH 由目标主机上的 Rust 伴侣程序提供（`portable-pty` 开本地终端 / `russh` 做 SSH）。P2P 通道只是把终端 I/O 透传过去。
- **建议**：与 2.2 绑定同一个「原生伴侣程序」决策。若做伴侣程序，这个顺带能做。

## 模块 3：实时音视频与趣味娱乐（核心卖点）

### 3.1 P2P 异地「一起看片房」 — ✅ 可行（建议改为同步播放游标，而非 P2P 传视频流）
- **能做**：每端各自播本地视频副本，**通过 DataChannel 同步播放游标**（NTP 式时钟偏移估计 + 播放速率微调 + 大偏差才 seek）。这是所有成熟看片方案（Jellyfin SyncPlay / Syncplay）的做法，能做到 **<100ms** 体感同步。
- **说明**：PRD 写「主控端加载本地 MP4，通过 DataChannel 实时传给房间所有人」——**真把视频流 P2P 分发**也能做（DataChannel/WebCodecs），但成本高、Mesh 分发扩展性差。**建议：默认「各播各的副本 + 同步游标」，把「主控推流给无副本的人」作为可选增强。** 需你确认走哪种。
- **建议**：Phase 3 亮点功能，建议做（同步游标方案）。

### 3.2 3D 空间音频虚拟办公室 — ✅ 可行（小房间）
- **能做**：Web Audio `PannerNode`（HRTF）+ `AudioListener`，头像距离映射音量。2D 地图 + 头像移动。
- **关键约束**：受 Mesh 上限约束（音视频 4–6 人；纯音频可更多）。**Chrome 有个坑**：来自 PeerConnection 的远端流必须同时挂到一个静音的 `<audio>` 元素上，Web Audio 才有声音。
- **建议**：Phase 4。做小规模挂机房（≤6 人视频 / 更多纯音频）。

### 3.3 闲置手机改「P2P 监控摄像头」 — ✅ 可行（但必须解决 HTTPS）
- **能做**：旧手机开网页当发送端 `getUserMedia`，常用设备当接收端看画面，数据 P2P 不过第三方云。
- **关键约束**：
  - `getUserMedia` **要安全上下文**——旧手机若通过 `http://局域网IP` 打开则用不了，必须 HTTPS（公网域名 + 证书，或 localhost 伴侣）。
  - 后台常驻受限：标签页切后台/息屏后采集会被挂起；需 Screen Wake Lock 且保持前台。旧手机长期当摄像头，浏览器方案并不稳，**原生伴侣程序更适合常驻**。
- **建议**：Phase 3/4。基础版=前台网页 + Wake Lock；「7×24 常驻」归入伴侣程序能力。

## 模块 4：网络优化与技术借力

### 4.1 P2P 内容去中心化加速（P2P CDN） — ⚠️ 可行但复杂，建议后置
- **能做**：同房间多人下同一文件/看同一视频源时，用 DataChannel 组 Mesh 互相拉分片（WebTorrent 式）。可参考维护中的 **P2P Media Loader**（配合 hls.js/Shaka）。
- **关键约束**：浏览器 WebTorrent **只能和 WebRTC 对端互通**，接不进传统 BT 网络；需要 wss tracker 做信令；Mesh 数据分发实际约 50–100 端会退化。
- **建议**：Phase 5+，等前面功能稳定后再评估。价值高但工程量大。
